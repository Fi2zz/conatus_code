# 人机双写故事层（可选）

故事层把每次编辑记成一条**补丁**，让 AI 与人共用同一条编辑历史。它从
cowriter 并入 nava，**默认关闭**：

```toml
[story]
enabled = true
```

关闭时（缺省）行为与普通编码会话完全一致：写工具直接落盘，不建故事线、
不装文件监听、不注入故事 prompt。开启后只影响 `write_file` / `edit_file` /
`apply_patch` 三个写工具；`git_*`、`run_command` 等编码工具不受影响。

## 块与补丁

- **块 = 段落**：文件按空行切段，每个段落是一个块，块 id 为
  `路径#<内容 sha1 前 8 位>`（同文件重复段落加 `-2`/`-3` 后缀）。超过 512 段的
  文件整体退化为 `路径#full` 单块。
- **一次成功的编辑 = 一个补丁**：`write_file` / `edit_file` / `apply_patch` 的
  成功结果各产生一条补丁（作者＝AI）；失败的工具调用不记。跨文件的
  `apply_patch` 是「一个补丁含多个 op」。
- **修改 = 删除旧段 + 插入新段**：差异由 LCS 对齐如实记为 remove + insert。
- **补丁随会话装配**：每次提交同步落 `doc/patch` 会话事件，重启后用
  `rebuildDocEngine` 从事件流重建故事线。数据落在项目数据目录下的
  `story-log/`（缺省 `~/.nava/projects/<编码工作区路径>/story-log/`）。

## 一轮协同怎么走

```
你：把这段开头改得更直接一些
AI：（调用 edit_file）→ 被审阅门拦下，登记为待定补丁，不落盘
    结果回给模型「编辑已登记为待定补丁 #1（1 个文件），待人审阅生效」
你：/story pending         ← 看待定补丁列表
你：/story apply 1         ← 接受，写盘并入故事线
    或 /story reject 1     ← 丢弃，文件原样不动
```

AI 收到的是「已登记」，不会因为「没写进去」而重试。

## 三条入故事的通道

1. **AI 工具编辑（受事前审阅）**：交互模式下三个写工具先算出「执行后的内容」
   登记为待定补丁，`/story apply` 后才写盘。算不出执行结果的调用
   （`edit_file` 的 old 串找不到、patch 上下文不适用、参数不全）**fail-open
   放行**给真实工具报错。headless 不拦截（无人审，文件必须真写）。
2. **人的编辑（轮询 + 内容归因）**：直接改工作目录下的文件，watcher 轮询
   （缺省 500ms，轮询间隔即防抖窗）把它登记为 human 补丁。归因靠内容对比：
   磁盘内容与引擎 fold 一致 → 是 AI 自己写的，跳过；不一致 → 人改的。
3. **`ops` 围栏块提议**：模型可用 ```` ```ops ```` 围栏块（JSON 数组的块操作）
   提议修改，只进待定列表，同样经 `/story apply` 审阅。

## `/story` 子命令

`preview` / `discard` / `fork` 取**时间轴序号**；`apply` / `reject` 取
**待定序号**。两套编号各自独立，别混用。

| 子命令 | 作用 |
|--------|------|
| `/story` | 补丁时间轴：序号、作者（人/AI）、补丁 id、涉及文件、落定时间 |
| `/story preview <n>` | 预览前 n 个补丁时刻的文档状态 |
| `/story discard <n>` | 驳回第 n 个补丁并把触及文件写回 fold 后内容 |
| `/story fork <n>` | 从前 n 个补丁分叉新会话并自动切换 |
| `/story pending` | 列出待定补丁（序号 + 来源 + ops 摘要） |
| `/story apply <i>` | 接受第 i 个待定补丁：写盘并入故事线 |
| `/story reject <i>` | 丢弃第 i 个待定补丁（不落盘） |

## diff 即反馈

人改文件时 watcher 生成摘要通报（每文件 `+N/-M` 行数，不带全文），经 steering
在 AI 组下一次模型请求前注入——AI 工作途中就能看到你改了哪些文件。需要细节
让它自己 `read_file`，避免把整段正文灌进上下文。

## 冲突：双版本落盘

待定补丁登记时记下每个目标文件的基底内容。`apply` 时若磁盘内容已不等于基底，
不覆盖也不静默失败：写一份 git 式 marker 的双版本合并文本（人的版本在上、
AI 待定内容在下），等人工合并；干净的文件照常写入。

## 与 `/rewind` 的分工

故事层管**文档内**的补丁历史（段落粒度、以编辑为单位）；`/rewind` 管**工作区级**
的时间回溯（文件快照 + 对话回滚）。`/story` 回答「这段文字是怎么变成现在这样的」，
`/rewind` 回答「把整个工作区退回三轮前」。

## 已知边界（v1）

- 文件删除不记 human 补丁（watcher 只处理 mtime 变新且内容不一致的文件）。
- `apply` 只支持 Insert / Replace；含 Remove / Move 的待定补丁 v1 拒绝应用。
- `/story fork` 出的分支是草稿线，不做分支间自动合并。
- 早期整文件粒度块不迁移（与新段落块共存）。
- 没有 `sessionLog` 服务时 `/story fork` 不可用（正常装配下不会出现）。
- 锚点批注、supersede、prompt 即补丁、patch 级 traveling 尚未实现。
